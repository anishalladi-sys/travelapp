# Prompt 06.4 — Observability and CI

## Goal
Make regressions visible and enforce repeatable CI verification without production side effects.

## Prerequisite
06.3 verified. Read `prompts/_CONVENTIONS.md` and `tasks/06-production/README.md`.

## Context and files
Inspect `.github/workflows/`, `playwright.config.ts`, `package.json`, Sentry config, and `next.config.ts`. Earlier inspection found E2E referencing absent tests, browser-install mismatch, duplicate server startup, and a health rewrite without its handler; recheck current state rather than assuming these still exist.

## Tasks
1. Establish one owner for Playwright web-server lifecycle. Install the browsers required by configured projects (including WebKit when selected); make CI use reproducible dependency installation and synthetic fixtures.
2. Run lint, project-wide typecheck, unit/integration tests, build, and E2E on PRs. Use an isolated local Supabase/test service for session and RLS integration, not production credentials. Preserve test evidence on failures; scrub screenshots/traces of real data.
3. Exercise signup/login, trip and itinerary CRUD, representative module mutations, and ownership through actual application paths. Demo mode cannot substitute for real-session integration.
4. Configure bounded, structured diagnostics and Sentry for client/server failures with verified SDK behavior. Disable default PII collection; redact tokens, URLs with signatures, request bodies, document fields, contacts, and location details. Use a synthetic error in a test environment to prove capture.
5. Implement or correct minimal `/health` handling without leaking environment/configuration. Distinguish process health from dependencies when relevant; bound timeouts and avoid noisy polling.
6. Document dashboard/alert ownership, key symptoms (errors/latency/failed uploads), deployment checks, rollback, and setup variable names. Changing branch protection or deploying requires explicit permission; report external configuration not yet applied.

## Acceptance criteria
CI definition covers all gates, test-server/browser setup is consistent, health behaves correctly, test telemetry is received and sanitized. Hosted CI/Sentry proof must be recorded separately from local runs; missing access remains blocked.

## Verification
`npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:e2e`; health smoke test, telemetry test, and hosted CI inspection where authorized. Do not commit/push solely to trigger CI. Apply shared completion procedure and stop.
