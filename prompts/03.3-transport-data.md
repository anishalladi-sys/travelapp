# Prompt 03.3 — Transport: Schema + Data + Actions

## Goal
Add the transport module backend, following the same pattern as 03.1.

## Prerequisite
Segment 03.1 marked ✅ (03.2 UI may run in parallel conceptually but execute
sequentially per tracker).

## Context
Same as 03.1: dual data mode, two migration copies, existing patterns in
`lib/data/` + `app/trips/` actions.

## Tasks
1. Zod schema `lib/validations/transport.ts`: type enum (flight/train/bus/
   ferry/car/other), provider optional, from_location, to_location,
   depart_at datetime, arrive_at optional (must be ≥ depart when present),
   booking_ref optional, cost/currency optional, notes optional.
2. Migration `transport` table: id, trip_id fk cascade, user_id, type,
   provider, from_location, to_location, depart_at, arrive_at, booking_ref,
   cost numeric, currency, notes, timestamps. RLS `auth.uid() = user_id`.
   BOTH migration copies + `SUPABASE_SETUP.md`.
3. Data layer `lib/data/transport.ts`: CRUD, ownership-scoped, sorted by
   depart_at. In-memory store equivalent.
4. Server actions `app/trips/[id]/transport/actions.ts`: Zod + requireUserId +
   ownership + revalidatePath, same error semantics as 03.1.
5. Tests: validation (arrive ≥ depart), CRUD, ownership isolation.

## Acceptance criteria
- CRUD works in both modes; RLS + action-level ownership enforced; tests green.

## Verification
- `npm test`, `npm run typecheck`, `npm run build`
- `npm run db:push` if dev credentials available, else deferred note.

Update `tasks/README.md` segment 03.3 when done.
